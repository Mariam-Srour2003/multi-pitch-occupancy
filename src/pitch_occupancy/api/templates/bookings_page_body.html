What booking data is for. The cameras say whether each pitch was actually played on. Your booking records say whether it was sold. Putting the two side by side shows games nobody booked, bookings nobody turned up for, and records that disagree. Booking data is optional - without it you still get the camera verdicts - and it is read-only: this system never changes anything in your booking system.

Your booking source

Where the bookings are read from. The settings live in a file on this machine, configs/bookings_source.json, which is never shared or uploaded because it can contain a database password.

How to connect your bookings

Create configs/bookings_source.json with one of these, then reload this page. Your own column names and status words can be kept - columns says which of your columns holds each value (ours are field_id, date, start, end, customer_ref, status, entered_by), and status_map translates your status words into ours: confirmed, cancelled, no_show, maintenance, blocked. If your start and end columns hold a full date and time, the date is taken from them. date_format / time_format handle other formats (for example %d/%m/%Y).

Databases: only a single SELECT query is accepted, but that check only catches mistakes. The real protection is to give this system its own database login that can only read the bookings table. Ask whoever runs your booking system for one. Databases other than SQLite also need two extra packages installed (for example uv add sqlalchemy psycopg2-binary for PostgreSQL).

Test the connection

Reads your booking source once and shows the first rows, so you can see the columns came through correctly.

Check booking data

Looks for problems that would make the comparison with the cameras wrong: missing or unreadable values, bookings that end before they start, unknown statuses, duplicates, double bookings, gaps. Every problem is listed at once. Nothing is saved.
